## ⚠️ MANDATORY: React SPA Prerender Architecture

This section is the #1 priority for all React (Vite + React Router) projects. Every rule below is non-negotiable.

### Why Prerender is Required

A React SPA has a single `index.html`. Without prerender:
- `view-source:` shows only the homepage HTML for ALL pages
- Google crawlers see wrong/missing metadata on inner pages
- PageSpeed scores suffer: browser must download JS → parse React → execute render → show content
- LCP/FCP/TBT metrics are structurally bottlenecked by the CSR pipeline
- `vendor-react` + `vendor-motion` bundles (200KB+) must load before any content appears

With build-time prerender:
- Every URL gets its own static HTML with correct `<title>`, `<meta>`, JSON-LD, OG tags baked in
- Browsers render content immediately → dramatically better LCP/FCP
- Google gets complete, crawlable HTML without executing JavaScript
- React hydrates afterward for interactivity — user experience unchanged

### Rules (Non-Negotiable)

1. **NEVER use `useEffect`, `document.title`, or client-side DOM manipulation for SEO tags.** This includes `applySeoMeta()` functions that modify `<head>` at runtime. These approaches silently fail for crawlers and hurt PageSpeed.

2. **SEO data = pure data objects** — export SEO metadata as plain TypeScript objects in `src/lib/seo-config.ts`. This file is the single source of truth.

3. **Build-time prerender script** — `scripts/prerender.mjs` runs after `vite build` and generates static HTML per route with correct `<head>` content. Script must be self-contained plain `.mjs` (no TypeScript imports).

4. **Build pipeline** — `"build": "vite build && node scripts/prerender.mjs"` in package.json

5. **Sitemap + robots.txt** — generated by the prerender script, NOT manually maintained as static files in `public/`

6. **Verify after every build** — grep `dist/` for page-specific titles to confirm prerender worked

### What This Replaces

These patterns are BANNED in new projects and should be migrated in existing ones:
- `applySeoMeta()` or any function that sets `document.title` / `meta` tags at runtime
- `useEffect(() => { document.title = "..." })`
- React Helmet / react-helmet-async
- Manually maintained `public/sitemap.xml` (prerender script generates it)
- Manually maintained `public/robots.txt` (prerender script generates it)

### Migration Path for Existing Projects

If a project currently uses client-side SEO (e.g., `applySeoMeta`):
1. Create `src/lib/seo-config.ts` with all route SEO data
2. Create `scripts/prerender.mjs` (see `references/prerender-script.mjs`)
3. Update `package.json` build script
4. Keep the runtime SEO calls as a fallback (they don't hurt, they're just redundant)
5. Delete manual `public/sitemap.xml` and `public/robots.txt`
6. Verify build output with grep tests

## PHASE 3 — CONTENT & CODE GENERATION

This is the biggest phase. It produces all React components and page content.

### Architecture: Reusable Component System
Build these shared components first — they're used across all pages:

| Component | Purpose |
|-----------|---------|
| `Layout.tsx` | Wraps Navbar + Footer around all pages, handles scroll-to-top |
| `PageHero.tsx` | Inner page hero banner (tag, h1 title, subtitle) |
| `FAQSection.tsx` | Accordion FAQ component, reused on every page |
| `BookingCTA.tsx` | Call-to-action section with phone + booking link |

### Data-Driven Content
Create `src/lib/page-content.ts` — a centralized file exporting all page text content as TypeScript objects. This separates content from components, making updates easier.

### Code Splitting
Use `React.lazy()` + `Suspense` for secondary pages (About, Contact, Locations overview, etc.). **DO NOT lazy-load SEO landing pages or the homepage** — these are the primary Google traffic targets and lazy loading adds a JS waterfall that kills LCP:

```tsx
// ✅ Eager-load: pages that receive organic search traffic
import Index from "./pages/Index";
import SeoLandingPage from "./pages/SeoLandingPage";

// ✅ Lazy-load: secondary pages that users navigate to from the site
const About = lazy(() => import("./pages/About"));
const Contact = lazy(() => import("./pages/Contact"));
```

**Why?** Lazy-loaded chunks create a serial download chain: `vendor-react.js` → parse → trigger lazy import → `SeoLandingPage.js` → render. This adds 500ms–1s to LCP on typical connections. Eager-loading lets all JS download in parallel.

### Parallelization Strategy
Phase 3 involves many files. Maximize speed by launching parallel agents:
- Agent 1: `seo-config.ts` (SEO metadata + JSON-LD schemas)
- Agent 2: `page-content.ts` (all page text content)
- Agent 3: Service page components (7+ files)
- Agent 4: Location + Guide page components (9+ files)
- Agent 5: Core pages (ServicesHub, About, Contact, FAQ) + App.tsx routing

### ⚠️ Slug Consistency Rule
Every agent prompt MUST include the complete slug list from `project.json.seo.pages[]`.
Internal links between pages are the #1 source of bugs — agents that don't see the exact
slugs will guess shorter paths (e.g., `/services/swedish-massage` instead of
`/services/swedish-massage-newberg`) and produce broken links across the entire site.

When writing agent prompts, always include a block like:
```
VALID SLUGS (use these EXACT paths for all internal links):
/services/swedish-massage-newberg
/services/deep-tissue-massage-newberg
...full list from project.json...
```

After all agents complete, grep for orphan links that don't match any registered route:
```bash
grep -roh 'to="[^"]*"' src/pages/ | sort -u  # compare against App.tsx routes
```

### Content Rules
- Respect `content_restrictions` from project.json (e.g., if "no_prices" → never show dollar amounts)
- Target keyword appears naturally 3-5x per page, no stuffing
- Tone: professional but warm, local and approachable
- Word count: Home 600-800w, Service 500-700w, Location 400-600w, Guide 700-1000w
- Always use actual city/neighborhood names — never "your city"
- Every page ends with a booking CTA
- **NEVER use contact forms / input fields on the Contact page.** Use `mailto:` links instead. A simple "Email Us" button with a `mailto:` href is sufficient. No form state, no form submission logic, no text inputs.
- **SEO tags are handled by prerender, NOT by page components.** Pages should NOT call applySeoMeta(), useEffect for document.title, or any runtime SEO function. SEO data lives in seo-config.ts and is injected by the prerender script at build time.

### Page Component Template
Each service/location/guide page follows this structure:
```
<PageHero tag="..." title="..." subtitle="..." />
<ContentSection> (intro + image, side by side)
<BenefitsSection> (bg-secondary, card grid)
<WhyChooseUs> (trust signals)
<FAQSection faqs={[...]} />
<RelatedServices> (links to 2-3 related pages)
<BookingCTA />
```

### Update Existing Components
Update the template project's existing Navbar, Footer, Hero, Services, About, Testimonials, and BookingCTA with real business data. Replace all placeholder text (business name, phone, address, hours, reviews).

### Routing: App.tsx
Register all routes in App.tsx with Layout wrapper:
```tsx
<Layout>
  <Suspense fallback={<Spinner />}>
    <Routes>
      <Route path="/" element={<Index />} />
      <Route path="/services" element={<ServicesHub />} />
      {/* ...all 21+ routes... */}
      <Route path="*" element={<NotFound />} />
    </Routes>
  </Suspense>
</Layout>
```

Run `npm run build` after all files are created. Fix any TypeScript/import errors before proceeding.

## PHASE 5 — TECHNICAL SEO PACK

See the Mandatory Prerender Architecture section above for context on why this phase is critical.

### The Prerender Script
The prerender script (`scripts/prerender.mjs`) is the core of the SEO pipeline. It runs after `vite build` and does six things in one pass:

1. **Prerenders every route `<head>`** — generates `dist/{route}/index.html` with page-specific `<title>`, `<meta description>`, `<link canonical>`, `<meta robots>`, OG/Twitter tags, and JSON-LD
2. **Injects page-specific SSR-fallback body content** — replaces the generic `<div id="ssr-fallback">` with inline-styled, page-specific `<h1>`, subheading, intro text, and location info. This IS the LCP element — see "SSR Fallback-as-LCP Strategy" section above.
3. **Injects early preload hints** — extracts CSS/JS URLs from Vite output and injects `<link rel="preload" as="style">` + `<link rel="modulepreload">` after `<meta viewport>` for faster resource discovery
4. **Strips unused vendor-motion modulepreloads** — removes `vendor-motion` chunk preloads from pages that don't use framer-motion (see pitfall #5)
5. **Generates `sitemap.xml`** — with priority tiers (Home 1.0 > Core 0.9 > Service 0.8 > Location 0.7 > Guide 0.6)
6. **Generates `robots.txt`** — with sitemap reference

The script must be **self-contained plain JavaScript** — it runs in Node.js outside the Vite/TS pipeline, so it cannot import `.ts` files. SEO data is duplicated in the script from `seo-config.ts`. This is intentional and unavoidable.

See `references/prerender-script.mjs` for the reference implementation.

### SSR-Fallback Body Pattern
Every page needs a `<div id="ssr-fallback">` inside `<div id="root">` with meaningful page content. React removes it on hydrate: `document.getElementById('ssr-fallback')?.remove()`.

The prerender script replaces the fallback content per route:
```html
<!-- Homepage -->
<div id="ssr-fallback">
  <h1>Business Name | Service in City</h1>
  <p>Description paragraph...</p>
  <h2>Services</h2>
  <h3>Service 1</h3><h3>Service 2</h3>
  <h2>Locations</h2>
  <p>Address — Phone</p>
</div>

<!-- SEO Landing Page -->
<div id="ssr-fallback">
  <h1>Service Name in City, ST</h1>
  <p>Subheading text</p>
  <p>Intro paragraph...</p>
  <p>Rating · Reviews · Locations</p>
  <h2>Our Locations</h2>
  <p>Location 1 address — phone</p>
  <p>Location 2 address — phone</p>
</div>
```

**Why this matters for LCP:** For text-only SEO landing pages, the LCP element is the `<h1>`. Without SSR fallback, `<h1>` only appears after: HTML download → JS download → React parse → render. With SSR fallback, `<h1>` appears as soon as HTML arrives — typically **< 1s** vs **3–5s**.

### Build Pipeline
```json
{
  "scripts": {
    "build": "vite build && node scripts/prerender.mjs"
  }
}
```

### Domain Configuration
The prerender script should read domain from `process.env.SITE_DOMAIN` with a sensible default:
```js
const DOMAIN = process.env.SITE_DOMAIN || "https://www.example.com";
```

## ⚠️ SSR Fallback-as-LCP Strategy (Critical for Sub-1s Mobile LCP)

The SSR-fallback `<div>` is not just a crawler aid — it is the **LCP element** on mobile. When done correctly, the browser paints the fallback `<h1>` and intro text as soon as HTML arrives (~0.6s on 4G), long before React boots up (~3–5s). This is the only way to achieve sub-1s LCP in a React SPA without migrating to SSR/SSG.

### Architecture

1. **Prerender script generates inline-styled fallback HTML** per route inside `<div id="ssr-fallback">`. The fallback must visually match the above-fold React layout so there is zero CLS when React replaces it.

2. **Sync removal script** — `<script>document.getElementById('ssr-fallback')?.remove()</script>` runs immediately after the fallback `<div>`. This removes the fallback before React mounts, preventing a double-paint flash.

3. **React's `createRoot().render()`** replaces all children of `<div id="root">` on first commit. The sync script ensures the fallback is already gone, so React renders into an empty container.

### Fallback HTML Rules

The prerender script must generate fallback HTML with **inline styles** that match the React component's computed layout:

```html
<div id="ssr-fallback">
  <div style="font-family:Lato,system-ui,sans-serif;max-width:72rem;margin:0 auto;padding:3rem 1rem">
    <h1 style="font-family:Playfair Display,serif;font-size:2.25rem;font-weight:600;color:#2F2A27;line-height:1.2">
      Service Name in City, ST
    </h1>
    <p style="font-size:1.5rem;color:#658066;font-weight:500;margin:0.75rem 0">Subheading</p>
    <p style="font-size:1.125rem;color:rgba(47,42,39,0.8);line-height:1.75;margin:1rem 0">Intro paragraph...</p>
    <p style="font-size:0.875rem;color:rgba(47,42,39,0.7);margin:1rem 0">Trust signals (rating, reviews, locations)</p>
    <h2 style="font-family:Playfair Display,serif;font-size:1.875rem;color:#2F2A27;margin:2rem 0 1rem">Locations</h2>
    <p style="font-size:0.875rem;color:rgba(47,42,39,0.8)">Address — Phone</p>
  </div>
</div>
```

Key matching rules:
- **Font families**: Use the same display/body fonts as the React theme (e.g., `Playfair Display` for headings, `Lato` for body)
- **Font sizes**: Match the React component's `text-*` Tailwind classes (e.g., `text-4xl` = `2.25rem`)
- **Colors**: Use the exact HSL/RGB values from the Tailwind theme, not Tailwind class names
- **Max-width + padding**: Match `container-spa` / `section-padding` utility classes
- **No images or complex layout**: Fallback is text-only for speed. Images load after React hydrates.

### When to Keep vs Remove the Sync Script

| Scenario | Sync removal? | Why |
|----------|--------------|-----|
| Fallback layout ≈ React layout | **Remove** sync script | Fallback stays visible as LCP, React seamlessly replaces it. Best LCP. |
| Fallback layout ≠ React layout | **Keep** sync script | Layout mismatch causes massive CLS. Better to remove early and let React paint fresh. |
| New project (built with this strategy) | **Remove** sync script | Design fallback to match from day one. |
| Legacy project (fallback is plain `<h1>` tags) | **Keep** sync script | Retrofitting pixel-perfect fallback is too risky mid-flight. |

### CLS Trap

If the fallback's visual height/layout doesn't match the React output, removing the sync script makes LCP faster but introduces **catastrophic CLS** (0.3+). The browser paints the simple fallback, then React replaces it with navbar + hero + grid → everything shifts. This is worse than a slow LCP.

**Rule:** Only remove the sync script when you are confident the fallback and React above-fold layouts produce the same visual bounding box.

### Performance Gains (Measured)

On simulated slow 4G (PageSpeed Insights mobile):
- **Without fallback-as-LCP**: LCP 3.5–5.4s (must wait for full JS pipeline)
- **With fallback-as-LCP (sync removal kept)**: LCP 1.5–2.5s (HTML arrives, but fallback removed before paint)
- **With fallback-as-LCP (sync removal removed, layout matches)**: LCP 0.6–1.0s (fallback IS the LCP paint)

### Prerender Script: Centralize Fallback Styles

Define fallback style constants at the top of the prerender script to avoid duplication:

```js
const FB = {
  wrap:  'font-family:Lato,system-ui,sans-serif;max-width:72rem;margin:0 auto;padding:3rem 1rem',
  h1:    'font-family:Playfair Display,serif;font-size:2.25rem;font-weight:600;color:#2F2A27;line-height:1.2',
  h2:    'font-family:Playfair Display,serif;font-size:1.875rem;color:#2F2A27;margin:2rem 0 1rem',
  sub:   'font-size:1.5rem;color:#658066;font-weight:500;margin:0.75rem 0',
  intro: 'font-size:1.125rem;color:rgba(47,42,39,0.8);line-height:1.75;margin:1rem 0',
  trust: 'font-size:0.875rem;color:rgba(47,42,39,0.7);margin:1rem 0',
  addr:  'font-size:0.875rem;color:rgba(47,42,39,0.8);margin:0.25rem 0',
};
```

Then use them consistently:
```js
function seoFallback(page) {
  return `<div style="${FB.wrap}">
    <h1 style="${FB.h1}">${page.h1}</h1>
    <p style="${FB.sub}">${page.subheading}</p>
    <p style="${FB.intro}">${page.intro}</p>
    ...
  </div>`;
}
```

### Project CLAUDE.md: Fallback Layout Contract (MANDATORY)

Every project using this strategy **MUST** document a "Fallback Layout Contract" in its `CLAUDE.md`. This section maps fallback inline styles to their React/Tailwind source of truth, so that changes to the React layout trigger corresponding updates to the prerender script.

Example CLAUDE.md section:
```markdown
## Fallback Layout Contract

The prerender script (`scripts/prerender.mjs`) generates SSR-fallback HTML with inline styles
that must match the React component layout. When changing any of these values, update BOTH sources.

| Fallback Style | React Source | Value |
|----------------|-------------|-------|
| `FB.wrap` max-width | `.container-spa` (index.css) | `72rem` / `max-w-7xl` |
| `FB.wrap` padding | `.section-padding` (index.css) | `3rem 1rem` / `py-10 px-4` |
| `FB.h1` font-family | `font-display` (tailwind.config) | Playfair Display |
| `FB.h1` font-size | `text-4xl` | `2.25rem` |
| `FB.h1` color | `--foreground` (index.css :root) | `#2F2A27` |
| `FB.sub` color | `--primary` (index.css :root) | `#658066` |
| `FB.intro` color | `text-foreground/80` | `rgba(47,42,39,0.8)` |
| Navbar height | `<Navbar>` component | ~64px (affects fallback top padding) |

**Rule:** Any PR that changes navbar height, font sizes, theme colors, or container widths
must also update the `FB` object in `scripts/prerender.mjs`. Forgetting this → CLS regression.
```

This contract prevents the #1 maintenance risk: changing the React layout without updating the prerender fallback, which silently re-introduces CLS.

## ⚠️ Common Performance Pitfalls (Learned from Production)

These are real bugs found in deployed local business sites. Check for these after every build.

### 1. Duplicate JSON-LD Schemas
**Bug:** Static JSON-LD in `index.html` + dynamic JSON-LD injected by React = Google sees "multiple aggregate ratings" on the same entity.
**Rule:** Use ONE source for structured data. If prerender injects JSON-LD, do NOT also have static JSON-LD in the source `index.html`. If legacy static schemas exist, remove them when adding prerender.
**Symptom:** Google Search Console reports "Review has multiple aggregate ratings — Items with this issue are invalid."

### 2. Global Hero Image Preload
**Bug:** `<link rel="preload" as="image" ...>` in `index.html` loads a large hero image on ALL routes, including text-only SEO landing pages that don't use it.
**Rule:** Conditional preload — only trigger on the homepage:
```html
<script>
if (location.pathname === '/') {
  var l = document.createElement('link');
  l.rel = 'preload'; l.as = 'image'; l.type = 'image/webp'; l.fetchPriority = 'high';
  l.imageSrcset = '/images/hero-640.webp 640w, /images/hero-1920.webp 1920w';
  l.imageSizes = '100vw';
  document.head.appendChild(l);
}
</script>
```
This runs synchronously in `<head>` so it's just as fast as a static `<link>` tag for the homepage, but doesn't waste bandwidth on other routes.

### 3. Lazy-Loading SEO Landing Pages
**Bug:** `React.lazy()` on SEO landing pages creates a 2-step JS waterfall (main bundle → lazy chunk). LCP measured at 5.4s in CrUX data.
**Fix:** Eager-import SEO landing page components. See Code Splitting section above.

### 4. framer-motion in Critical Path
**Rule:** Never import `framer-motion` in Layout, Navbar, Footer, or any component loaded on every page. Only use it in lazy-loaded secondary pages. The `vendor-motion` chunk is ~40KB gzip and blocks render if it's in the critical path.

### 5. vendor-motion modulepreload on Non-Motion Pages
**Bug:** Vite's code-split output includes `<link rel="modulepreload" href="vendor-motion-*.js">` on ALL pages, even text-only SEO landing pages that never use framer-motion. This wastes ~120KB of bandwidth.
**Rule:** The prerender script should strip vendor-motion modulepreloads from pages that don't use motion:
```js
const MOTION_PAGES = new Set(["/services", "/locations", "/about", "/contact"]);

function stripUnusedModulePreloads(html, route) {
  if (!MOTION_PAGES.has(route)) {
    html = html.replace(/<link\s+rel="modulepreload"\s+crossorigin\s+href="[^"]*vendor-motion[^"]*">\n?/g, "");
  }
  return html;
}
```

### 6. Non-Composited CSS Animations
**Bug:** Using `filter: drop-shadow()` in CSS keyframes triggers non-composited animations. PageSpeed flags "Avoid non-composited animations" for every animated element.
**Rule:** Only animate `opacity` and `transform` in keyframes (these are GPU-composited). Apply `filter` as a static property, not inside `@keyframes`. Add `will-change: opacity` or `will-change: transform` to animated elements.

### 7. Oversized Logo Images
**Bug:** Logo rendered at 216×122px but source image is 1472×832 (52KB). PageSpeed flags "Properly size images."
**Rule:** Resize logos to 2× display size (e.g., 432×244 for 216×122 display). Use WebP. Target < 15KB for logos.

### 8. Google Fonts Blocking Render (External Request Overhead)
**Bug:** `@import url('https://fonts.googleapis.com/...')` in CSS or `<link rel="stylesheet" href="https://fonts.googleapis.com/...">` in HTML requires 3 external network hops: DNS → fonts.googleapis.com CSS → fonts.gstatic.com woff2. On mobile 4G this adds 300-500ms to FCP.
**Rule:** Self-host fonts. Download only the latin subset woff2 files and serve from the same domain:

**Step-by-step:**
```bash
# 1. Identify which font files you need (use mobile UA to get woff2)
curl -H "User-Agent: Mozilla/5.0 (Linux; Android 10) AppleWebKit/537.36 Chrome/120.0.0.0 Mobile Safari/537.36" \
  "https://fonts.googleapis.com/css2?family=Inter:wght@300;400;500;600&display=swap"

# 2. Download the latin subset woff2 file (last @font-face block in response)
# Save to public/fonts/inter-latin.woff2

# 3. Repeat for each font family (e.g., Cormorant Garamond, Playfair Display, Lato)
```

**Create `public/fonts/fonts.css`:**
```css
@font-face {
  font-family: 'Inter';
  font-style: normal;
  font-weight: 300 600;
  font-display: swap;
  src: url('/fonts/inter-latin.woff2') format('woff2');
  unicode-range: U+0000-00FF, U+0131, U+0152-0153, U+02BB-02BC, U+02C6, U+02DA, U+02DC, U+0304, U+0308, U+0329, U+2000-206F, U+20AC, U+2122, U+2191, U+2193, U+2212, U+2215, U+FEFF, U+FFFD;
}

@font-face {
  font-family: 'Playfair Display';
  font-style: normal;
  font-weight: 400 700;
  font-display: swap;
  src: url('/fonts/playfair-display-latin.woff2') format('woff2');
  unicode-range: U+0000-00FF, U+0131, U+0152-0153, U+02BB-02BC, U+02C6, U+02DA, U+02DC, U+0304, U+0308, U+0329, U+2000-206F, U+20AC, U+2122, U+2191, U+2193, U+2212, U+2215, U+FEFF, U+FFFD;
}
```

**Update `index.html` — preload fonts + use local CSS (remove all Google Fonts links):**
```html
<link rel="preload" href="/fonts/inter-latin.woff2" as="font" type="font/woff2" crossorigin />
<link rel="preload" href="/fonts/playfair-display-latin.woff2" as="font" type="font/woff2" crossorigin />
<link rel="stylesheet" href="/fonts/fonts.css" />
```

**Remove from `index.css`:**
```css
/* DELETE this line — font loaded via HTML now */
@import url('https://fonts.googleapis.com/css2?family=...');
```

**Key points:**
- Use `font-weight: 300 600` range syntax for variable fonts (one file covers multiple weights)
- Only download latin subset (`unicode-range`) — saves 60-80% vs full character set
- `font-display: swap` prevents invisible text during load
- `rel="preload"` starts font download immediately, before CSS is parsed
- Total font budget: ~70KB for 2 font families (vs 100KB+ from Google + 3 network round trips)
- Result: **zero external font requests**, fonts load in parallel with CSS/JS from same CDN

**Python helper script for downloading fonts:**
```python
import urllib.request, re, os

def download_google_font(family, weights, output_dir="public/fonts"):
    """Download latin-only woff2 from Google Fonts and generate @font-face CSS."""
    os.makedirs(output_dir, exist_ok=True)
    family_param = family.replace(" ", "+")
    weights_param = ";".join(weights)
    url = f"https://fonts.googleapis.com/css2?family={family_param}:wght@{weights_param}&display=swap"
    headers = {"User-Agent": "Mozilla/5.0 (Linux; Android 10) AppleWebKit/537.36 Chrome/120.0.0.0 Mobile Safari/537.36"}
    req = urllib.request.Request(url, headers=headers)
    css = urllib.request.urlopen(req).read().decode()

    # Find all woff2 URLs - last one is typically latin
    urls = re.findall(r'url\((https://[^)]+\.woff2)\)', css)
    latin_url = urls[-1]  # Latin is always last

    slug = family.lower().replace(" ", "-")
    fname = f"{slug}-latin.woff2"
    filepath = os.path.join(output_dir, fname)
    urllib.request.urlretrieve(latin_url, filepath)

    size_kb = os.path.getsize(filepath) / 1024
    print(f"{family}: {size_kb:.1f}KB -> {filepath}")
    return fname

# Usage:
# download_google_font("Inter", ["300", "400", "500", "600"])
# download_google_font("Playfair Display", ["400", "500", "600", "700"])
```

### 9. Unnecessary Preconnects for Deferred Scripts
**Bug:** `<link rel="preconnect" href="https://www.googletagmanager.com">` in `<head>` opens a TCP+TLS connection immediately, but GA doesn't load until 5s after page load. The connection times out and wastes resources.
**Rule:** Only preconnect to origins needed in the first 2-3 seconds. For deferred scripts (GA, widgets), skip preconnect entirely.

### 9. GA4 Blocking Main Thread
**Bug:** `<script async src="gtag.js">` in `<head>` downloads and executes during page load, adding ~200ms to TBT.
**Rule:** Defer GA to `requestIdleCallback` after `window.load`:
```html
<script>
window.addEventListener('load', function() {
  function go() { /* create script, init gtag */ }
  if ('requestIdleCallback' in window) {
    requestIdleCallback(go, { timeout: 5000 });
  } else {
    setTimeout(go, 4000);
  }
});
</script>
```

### 10. Cloudflare Pages Trailing Slash Breaking SPA Routes
**Bug:** Cloudflare Pages returns 308 redirect adding trailing slash (e.g., `/massage-near-me` → `/massage-near-me/`). React Router matches against the trailing-slash path, which doesn't match the route map key, so the page falls through to the catch-all and redirects to homepage.
**Rule:** Normalize `useLocation().pathname` in route-matching components:
```tsx
const { pathname: raw } = useLocation();
const pathname = raw.endsWith('/') && raw !== '/' ? raw.slice(0, -1) : raw;
```

### 11. Unused Dependencies Bloating JS Bundle
**Bug:** Template projects (Lovable, shadcn/ui starter) ship with 30+ unused packages: @tanstack/react-query, recharts, react-day-picker, embla-carousel, react-hook-form, zod, vaul, cmdk, input-otp, date-fns, next-themes, plus 40+ unused @radix-ui packages. These all get bundled even if unused by tree-shaking failures.
**Rule:** After finishing Phase 3, audit and remove unused packages:

```bash
# 1. Find which @radix-ui packages are actually imported in app code (NOT in ui/ folder)
grep -r "from \"@radix-ui" src/ --include="*.tsx" | grep -v "src/components/ui/"

# 2. Find which ui/ components are actually imported by app code
grep -r "from \"@/components/ui/" src/ --include="*.tsx" | grep -v "src/components/ui/"

# 3. Delete unused ui/ components
rm src/components/ui/{calendar,chart,carousel,drawer,command,form,input-otp,resizable,...}.tsx

# 4. Uninstall unused packages
npm uninstall @tanstack/react-query recharts react-day-picker embla-carousel-react \
  react-hook-form @hookform/resolvers zod react-resizable-panels input-otp cmdk \
  date-fns next-themes vaul
```

**Measured impact:** JS bundle 413KB → 210KB (main + vendor), CSS 80KB → 41KB. This alone can improve PageSpeed mobile score by 10-15 points.

### 12. Image Optimization Checklist
**Rule:** Before production build, optimize all images:

```python
from PIL import Image
import os

for f in os.listdir("src/assets"):
    if f.endswith(".jpg"):
        path = f"src/assets/{f}"
        img = Image.open(path)
        w, h = img.size
        # Resize if larger than 800px (sufficient for 2x retina at 400px display)
        max_size = 800
        if w > max_size or h > max_size:
            ratio = min(max_size/w, max_size/h)
            img = img.resize((int(w*ratio), int(h*ratio)), Image.LANCZOS)
        img.save(path, "JPEG", quality=80, optimize=True)
```

**Rules:**
- Max dimension: 800px (covers 2x retina for typical 400px mobile display)
- JPEG quality: 75-80 (visually identical, 30-50% smaller)
- All `<img>` must have explicit `width` and `height` attributes (prevents CLS)
- Hero/above-fold images: NO `loading="lazy"` (blocks LCP)
- Below-fold images: ALWAYS `loading="lazy"`
- Logos: PNG with transparency, target < 15KB

### 13. Vite Build Optimization Config
**Rule:** Always configure manual chunks and build target:

```typescript
// vite.config.ts
export default defineConfig({
  build: {
    target: "es2020",
    cssMinify: true,
    rollupOptions: {
      output: {
        manualChunks: {
          vendor: ["react", "react-dom", "react-router-dom"],
        },
      },
    },
  },
});
```

This separates the vendor chunk (React + Router, ~53KB gzip) from app code (~12KB gzip for homepage). Vendor chunk is long-term cacheable across deploys.

### 14. ScrollToTop for React Router SPA
**Bug:** React Router client-side navigation doesn't scroll to top on page change. Users click nav links and land in the middle of the new page.
**Rule:** Add ScrollToTop component inside BrowserRouter:

```tsx
const ScrollToTop = () => {
  const { pathname } = useLocation();
  useEffect(() => { window.scrollTo(0, 0); }, [pathname]);
  return null;
};

// In App.tsx:
<BrowserRouter>
  <ScrollToTop />
  <Routes>...</Routes>
</BrowserRouter>
```

**Warning:** Do NOT use `scroll-behavior: smooth` on `html` — it makes page transitions slowly scroll up instead of instant jump. Use `scrollIntoView({ behavior: "smooth" })` only for in-page anchor scrolling.

## Google PageSpeed Insights — Scoring Rules

Target: **90+ on mobile, 95+ on desktop** for all pages. These are the metrics Google uses for Core Web Vitals and page ranking.

### Core Web Vitals Thresholds

| Metric | Good | Needs Improvement | Poor |
|--------|------|-------------------|------|
| **LCP** (Largest Contentful Paint) | ≤ 2.5s | 2.5–4.0s | > 4.0s |
| **INP** (Interaction to Next Paint) | ≤ 200ms | 200–500ms | > 500ms |
| **CLS** (Cumulative Layout Shift) | ≤ 0.1 | 0.1–0.25 | > 0.25 |

### Additional PageSpeed Metrics

| Metric | Target | How to Hit It |
|--------|--------|---------------|
| **FCP** (First Contentful Paint) | ≤ 1.8s | SSR-fallback body content baked in HTML |
| **TBT** (Total Blocking Time) | ≤ 200ms | Defer 3rd-party scripts (GA, widgets); code-split non-critical JS |
| **Speed Index** | ≤ 3.4s | Prerender + font `display=swap` + conditional image preload |

### Practical Rules for Local Business SPA Sites

**LCP (most common fail):**
- Text-only pages: LCP = `<h1>` text. Ensure SSR-fallback has the `<h1>` in static HTML so it renders before JS.
- Image hero pages: Use `<link rel="preload">` for the hero image (but only on pages that use it — see pitfall #2).
- Google Fonts: Use `preload as="style"` with `display=swap`. Never block render on custom fonts.
- Bundle size: Keep critical-path JS under ~170KB gzip. Split vendor chunks (react, framer-motion, icons).

**CLS (common fail):**
- Set explicit `width` and `height` on all `<img>` tags.
- Reserve space for dynamic content (banners, accordions) with min-height or aspect-ratio.
- Web fonts: use `font-display: swap` and size-adjust fallback to minimize layout shift on font load.
- Never inject content above the fold after initial render (e.g., cookie banners should use `position: fixed`).

**TBT / INP:**
- Defer GA4: load via `setTimeout` after `window.load` (3–5s delay is fine).
- Defer 3rd-party widgets (booking, chat, review widgets): 5s+ post-load.
- Never use synchronous `<script>` tags in `<head>` except tiny inline scripts.
- Avoid `framer-motion` animations on initial render — use CSS transitions for above-the-fold content.

**PageSpeed-Specific Audit Items:**
- "Eliminate render-blocking resources" → async/defer all scripts, preload fonts as style
- "Reduce unused JavaScript" → code-split, tree-shake, lazy-load secondary routes
- "Serve images in next-gen formats" → all images must be WebP or AVIF
- "Properly size images" → responsive `srcset` with 640/1024/1920 breakpoints
- "Enable text compression" → hosting must serve gzip/brotli (Cloudflare/Vercel do this automatically)
- "Avoid enormous network payloads" → total page weight < 500KB for text pages, < 1.5MB for image-heavy pages

## SEOptimer / SEO Audit Tool — Scoring Rules

These rules ensure the site passes automated SEO audits (SEOptimer, Ahrefs Site Audit, Screaming Frog, Lighthouse SEO).

### On-Page SEO (Per Page)

| Check | Rule | Common Fail |
|-------|------|-------------|
| **Title tag** | Present, 30–60 chars, includes target keyword + city + brand | Too long (truncated in SERP), missing keyword |
| **Meta description** | Present, 120–160 chars, includes keyword + CTA ("Book today") | Missing entirely, or duplicate across pages |
| **H1 tag** | Exactly one per page, includes target keyword | Multiple H1s, or H1 missing on inner pages |
| **H2 tags** | 2–5 per page for content structure | Zero H2s on landing pages |
| **Canonical tag** | Present, self-referencing, absolute URL | Missing, or pointing to wrong URL |
| **Open Graph tags** | `og:title`, `og:description`, `og:image`, `og:url`, `og:type` all present | Missing `og:image` (social shares look broken) |
| **Twitter Card tags** | `twitter:card`, `twitter:title`, `twitter:description`, `twitter:image` | Missing entirely |
| **Image alt text** | Every `<img>` has descriptive `alt` attribute | Decorative images with empty alt (use `alt=""` intentionally for decorative only) |
| **Internal links** | Every page links to 2–3 related pages + homepage | Orphan pages with no internal links |
| **Content length** | Minimum 300 words per indexable page | Thin content on service/location pages |
| **Keyword density** | Target keyword 3–5 times naturally, no stuffing | Over-optimization or keyword absent |
| **Mobile viewport** | `<meta name="viewport" content="width=device-width, initial-scale=1.0">` | Missing viewport tag |
| **Language** | `<html lang="en">` (or appropriate language) | Missing lang attribute |
| **Robots meta** | `<meta name="robots" content="index,follow">` on public pages | noindex accidentally set |

### Technical SEO (Site-Wide)

| Check | Rule | Common Fail |
|-------|------|-------------|
| **SSL/HTTPS** | All pages served over HTTPS, no mixed content | HTTP images or scripts |
| **robots.txt** | Present at `/robots.txt`, allows crawling, references sitemap | Accidentally blocking crawlers |
| **sitemap.xml** | Present at `/sitemap.xml`, lists all public URLs, valid XML | Stale/manual sitemap with missing pages |
| **Favicon** | Present at `/favicon.ico` | Missing (shows broken icon in tabs/bookmarks) |
| **404 page** | Custom 404 with navigation back to site | Default server 404 or blank page |
| **Page speed** | Mobile score ≥ 80 (target 90+) | See PageSpeed section above |
| **Structured data** | Valid JSON-LD on every page, no errors in Google Rich Results Test | Duplicate schemas, missing required fields |
| **URL structure** | Lowercase, hyphens, descriptive, no trailing slashes (except root) | Uppercase letters, underscores, IDs in URLs |
| **Redirect chains** | No chain > 1 hop, no redirect loops | /old → /middle → /new (should be /old → /new) |
| **Duplicate content** | No two pages with identical title or description | Template pages with same default meta |

### Schema Markup Rules

| Schema Type | When to Use | Required Fields |
|-------------|-------------|-----------------|
| `LocalBusiness` / `DaySpa` | Homepage, location pages | name, address, telephone, openingHours, geo, url, aggregateRating |
| `Service` | Service/SEO landing pages | name, description, provider, areaServed |
| `FAQPage` | Pages with FAQ sections | mainEntity → Question[] → acceptedAnswer |
| `BreadcrumbList` | All inner pages | itemListElement with position, name, item(url) |

**Schema pitfalls:**
- NEVER put the same `@id` on two different JSON-LD blocks — Google merges them and reports conflicts
- NEVER duplicate `aggregateRating` across static and dynamic schemas
- Always validate at https://search.google.com/test/rich-results before deploy
- `@type` must match the business: use `DaySpa` for spas, `MassageTherapy` for massage-only, `BeautySalon` for salons

### Social Media / Link Preview

| Platform | Required Tags | Image Size |
|----------|--------------|------------|
| Facebook/Meta | `og:title`, `og:description`, `og:image`, `og:url` | 1200×630px |
| Twitter/X | `twitter:card=summary_large_image`, `twitter:title`, `twitter:description`, `twitter:image` | 1200×628px |
| LinkedIn | Uses OG tags | 1200×627px |

**Rule:** Always have one high-quality 1200×630 OG image in the `public/` directory. Reference it in both `og:image` and `twitter:image`. The prerender script should set this on every page.

## Page Hierarchy & Navigation Strategy

Service detail pages (`/services/*`), location pages (`/locations/*`), and guide pages (`/guides/*`) are **long-tail SEO landing pages** — they exist to capture search traffic and upsell, NOT as part of the main user navigation flow.

### Rules:
- **ServicesHub (`/services`)** should display service cards with a direct **"Book Now"** button linking to the booking platform (e.g., MassageBook). Do NOT use "Learn More" links that navigate to individual service detail pages.
- **Service detail pages** are reached organically via Google search, internal links from guides/location pages, or the SEO keyword dashboard — never from the main services listing.
- **Location pages** and **guide pages** follow the same pattern: they are entry points from search engines that funnel users toward booking.
- The main site navigation (Navbar) should link to core pages only: Home, Services (hub), About, Contact, FAQ. Do NOT put individual service/location/guide pages in the nav.
